# Getting Started with Chipyard

> **If you are not using Docker and installed Chipyard natively on Linux:** skip `docker compose run --rm chipyard` and run `source scripts/native-activate.sh` from your clone instead. In every command in this guide, replace `/workspace` with `$WS`. For example, `cd /workspace/chipyard` becomes `cd $WS/chipyard`. See [Native Installation](/docs/native-install.md), Sections 5 and 6.

This guide introduces the Chipyard environment used in this course. Before continuing, complete the installation steps in the repository's main `README.md` and verify that the environment test passes.

## 1. Start the Course Environment

From the root directory of the course repository on your computer, start the Chipyard Docker container:

```bash
docker compose run --rm chipyard
```

You should now have a shell inside the course container.

The Chipyard installation is located at:

```text
/workspace/chipyard
```

Your persistent working directory is:

```text
/workspace/student-work
```

Files placed in `/workspace/student-work` are stored in the `student-work/` directory of the repository on your computer and will remain available after the container exits.

> **Important:** Do not use the Docker container itself as permanent storage. Store work that you want to keep in `/workspace/student-work` or another directory specifically identified by an assignment.

> **If you are not using Docker and installed Chipyard natively on Linux:** instead of starting the container, run this from your clone:
>
> ```bash
> source scripts/native-activate.sh
> ```
>
> Chipyard is in `$WS/chipyard` and your persistent directory is `$WS/student-work`. Everything in your clone persists between sessions, including `chipyard/`.

---

## 2. Load the Chipyard Environment

Before using the RISC-V toolchain or Chipyard, load the Chipyard environment:

```bash
cd /workspace/chipyard
source env.sh
```

You will generally need to run `source env.sh` each time you start a new container.

You can verify that the RISC-V compiler is available with:

```bash
which riscv64-unknown-elf-gcc
```

This should return the location of the RISC-V cross-compiler.

---

## 3. The Course Processor Configuration

The standard processor configuration for this course is:

```text
CourseRocketConfig
```

It is based on the RISC-V Rocket processor provided through Chipyard.

Unless an assignment explicitly instructs you otherwise, use `CourseRocketConfig` as the baseline processor for course experiments and project.

Do **not** modify Chipyard's standard `RocketConfig`. Keeping the original configuration unchanged gives us a known reference architecture against which modified designs can be compared.

---

## 4. Build the Course Rocket Simulator

Chipyard can generate a software simulator of the hardware using Verilator.

Move to the Verilator simulation directory:

```bash
cd /workspace/chipyard/sims/verilator
```

Build the course processor:

```bash
make CONFIG=CourseRocketConfig
```

The first build can take some time.

When the build completes, the generated simulator will be located in this directory with a name similar to:

```text
simulator-chipyard.harness-CourseRocketConfig
```

You generally do not need to rebuild the simulator unless the hardware configuration or processor implementation has changed.

---

## 5. Run a RISC-V Program

After loading the Chipyard environment and building the simulator, you can run a RISC-V executable on the simulated processor.

For example, run one of the RISC-V ISA tests:

```bash
./simulator-chipyard.harness-CourseRocketConfig \
  $RISCV/riscv64-unknown-elf/share/riscv-tests/isa/rv64ui-p-simple
```

A successful simulation should terminate with a passing result rather than an error.

This is a **hardware simulation**: the RISC-V program is executing on the Rocket processor model generated by Chipyard.

## 6. Understanding the Workflow

Most experiments in this course will follow the same general workflow:

```text
Application / benchmark
        |
        v
Compile for RISC-V
        |
        v
Choose or modify a Chipyard configuration
        |
        v
Build the Verilator simulator
        |
        v
Run the application
        |
        v
Collect performance statistics
        |
        v
Analyze the architectural behavior
```

A few important things to note:

* **Changing the application** normally requires recompiling the RISC-V program.
* **Changing the hardware architecture** normally requires rebuilding the Verilator simulator.
* **Running another input on unchanged hardware** normally does not require rebuilding the processor.

Understanding these will save considerable simulation time.

## 8. Course Philosophy

Throughout the semester, we will use the same basic RISC-V architecture and application workloads to investigate different computer architecture concepts.

Rather than treating each topic as an isolated exercise, we will repeatedly ask:

> **What limits the performance of this application, and what architectural change can improve it?**

Depending on the assignment (and your project), you may investigate factors such as:

* instruction execution and CPI,
* pipelining and pipeline hazards,
* branch behavior and branch prediction,
* cache organization,
* memory hierarchy,
* architectural specialization, and
* hardware acceleration.

You will often be asked to **predict the effect of an architectural change before running the simulation**, measure the actual result, and explain any difference between your prediction and the observed behavior.

Some of the take-home quizzes will require you to run experiments to gather the numbers needed for the quizzes.

---

## 9. Important Rules

Unless an assignment says otherwise:

1. Use `CourseRocketConfig` as the baseline processor.
2. Do not modify Chipyard's standard `RocketConfig`.
3. Do not modify files under `generators/rocket-chip` unless specifically instructed.
4. Keep files that must persist in `/workspace/student-work`.
5. Record the configuration, workload, and relevant simulation results for each experiment.
6. Do not assume that an architectural change improves performance; measure it.
